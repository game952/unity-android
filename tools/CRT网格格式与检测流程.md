# CRT 网格格式与检测流程 (verify_v481f / PreviewV4 v4.8.1e)

> 一句话: 改 PreviewV4.cs 解析逻辑前/后, 用 verify 脚本在真机对 pak_out 样张闭环验收; **全绿才允许提交装包**。

## 用法

```bash
python /sdcard/Download/verify_v481f.py                  # 全量 17 项 (12 ski + 4 act + 1 动画变体)
python /sdcard/Download/verify_v481f.py --dump a_wt_m_sho_00   # 单文件深诊断
```

- 脚本内用绝对路径指向 pak_out, 放在仓库任何位置都能跑;
- 开头第一行是**内置自检** (合成样张), 自检挂了 = 脚本本身坏了, 别信当轮结果;
- FAIL 自动附诊断: 四种链变体、计数器搜索、LE/BE/u32 段扫描、流后尾巴 hex、CRT_Mtl 位置。

## PASS 判据 (与 C# ParseSki 同判据)

- **ski**: 顶点流链长 == 计数器 vcp (互证); 面数 ≥ max(3, vcp//10) — "1 个面"的假通过会被拦截转 FAIL;
- **act**: 点数 > 0 且节点表/锚名合理;
- 面数与 1051÷3=350 这类整数关系对得上, 才是真表。

## 格式定案 (v4.8.1e, 全部指纹实证)

| 要素 | 定案 |
|---|---|
| ski 顶点流 | LE 自校验记录链: nbk(u32) + 骨id(1B/骨) + 权重(f32/骨) + pos/normal/tangent(f32×3) + uv(f32×2); 流一直吃到文件尾 |
| ski 面表 | 头部后 ≈0x4E 起, **大端 u16** 三元组; 被 CRT_Mtl 打断成多段, 按产量贪心合并 |
| ski 计数器 | vcp(u32 LE) 在流前 24B, 与链长互证 |
| act 网格 | 全域签名扫描 `[u32 V][V×3 合理浮点]`; 节点表之间藏变换数据, 逐节点走查必漏 |

## 血泪陷阱 (排查时先对号入座)

1. **大端冤案**: v4.7 用大端读面表被判"碎片化根因", 实际错在顶点流定位; 面表确实是大端。别再改回小端。
2. **幽灵段双倍计数**: LE 表做 BE 奇对齐扫描会原样复刻同值序列 → 面数翻倍。对策 = "产量为王": 候选段按长度降序贪心, 重叠过半跳过, **产出为零不占位**。
3. **奇数字节对齐**: CRT_Mtl 块 7 字节会把面表顶到奇地址 → 段扫描必须双对齐 (par 0/1 都扫)。
4. **整表错位**: 段头零填充长度非 3 倍数 → 全部三角形顶点错连成细碎片。FlushRun 对 shift 0/1/2 各数一遍有效面取最多。
5. **节点表陷阱**: ACT 点表之间的 u32 是变换数据不是点数 → 只能全域签名扫描。
6. **假通过**: 只有 1~2 个面的 PASS 是垃圾段幸存 → 假通过拦截 (面 < max(3, vcp//10) 即 FAIL)。
7. **索引越界**: 面索引 ≥ vcp 的三角形必须丢弃 (防 Unity mesh 越界崩溃), 留洞好过崩溃。

## 与 C# 的对应关系

`verify_v481f.py` 的 `parse_ski / collect_runs / flush_run / act 签名` 与 `PreviewV4.cs` 的 `ParseSki / CollectRuns / FlushRun` 逐行同构。**改一侧必须同步另一侧并跑本脚本**, 这是铁律。
